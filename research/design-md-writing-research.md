# 如何写好项目 `design.md`：一手资料调研与 Living Reader 建议

> 日期：2026-08-09
> 范围：项目级产品设计文档，不是单个组件说明或纯技术架构文档
> 结论状态：Research v1，尚未据此改写根目录 `design.md`

## 结论

高质量 `design.md` 不是审美宣言、需求清单或当前实现截图的集合。它是一份**可审查、可执行、可验收、可演进的设计合同**，至少应让新加入的人回答：

1. 我们在解决谁的什么问题，证据是什么？
2. 这一版明确追求什么，又明确不做什么？
3. 用户会经历怎样的状态与可见结果？
4. 为什么选择这个方案，拒绝了哪些方案？
5. 哪些结论已经确定，哪些仍在讨论，由谁、用什么证据裁决？
6. 实现后如何证明设计目标真的成立？
7. 当设计变化时，文档怎样留下理由而不是只覆盖结果？

对 Living Reader，根目录 `design.md` 最适合承担“**产品设计宪法 + 决策索引**”，不应吞并架构协议、任务状态、完整视觉规范和每轮审计证据。

## 一手资料中的共同模式

### Kubernetes：先写动机、边界、风险和验证，再谈实现完成

Kubernetes 的 KEP 模板把 `Summary`、`Motivation`、`Goals`、`Non-Goals`、`Proposal`、用户故事、风险、设计细节、测试计划、成熟标准、回滚、依赖、备选方案和实施历史放在同一生命周期中。它还明确建议早期合并高层内容、持续迭代，而不是等实现完成才补文档。

这说明设计文档首先是一套**讨论和收敛机制**，不是事后说明书。来源：[Kubernetes KEP 模板](https://github.com/kubernetes/enhancements/blob/master/keps/NNNN-kep-template/README.md)。

### Rust：必须把“方案是什么”和“为什么是它”分开

Rust RFC 模板区分：动机、面向使用者的解释、精确规范、缺点、理由与备选、先例、未决问题和未来可能性。尤其重要的是：记录备选方案并不代表当前方案不坚定，而是让后来的人知道团队比较过什么、为什么没有采用。

这说明 `design.md` 不能只有“我们要这样做”，还要保留**决策理由和被拒绝方案**。来源：[Rust RFC 模板](https://github.com/rust-lang/rfcs/blob/master/0000-template.md)。

### Python：文档需要明确状态和生命周期

Python PEP 1 把提案定义为简洁的技术规范及其理由，并使用 Draft、Accepted、Final、Deferred、Rejected、Withdrawn 等状态管理生命周期；进入 Final 还需要参考实现完成。它也要求处理兼容性，而不是只描述理想状态。

这说明设计文档顶部应有可读的状态、负责人和更新时间；“已讨论”“已接受”“已实现”“已验证”不能混成一个模糊的“当前基线”。来源：[PEP 1](https://peps.python.org/pep-0001/)。

### W3C TAG：原则必须有证据、能跨场景成立并体现价值取舍

W3C TAG 对设计原则的要求包括：基于规范、实现或真实使用模式；有证据；能跨技术和场景复用；具有时间稳定性；由清楚的价值或优先级指导，例如偏好简单、保护用户自主权；并与既有原则兼容。

这说明“像 Apple”“克制”“内容优先”还不够。原则必须被翻译成**可观察规则**，例如“首屏只有一个主动作”“工程证据默认折叠但可访问”。来源：[W3C Web Platform Design Principles](https://github.com/w3ctag/design-principles)。

### Apple：Apple 感来自清晰、邻近、触达和反馈，不是表面材质

Apple HIG 的职责是提供跨 Apple 平台的体验指导；Apple 的 UI Design Tips 进一步给出可检查的界面条件，例如触控目标至少 44×44pt、文字可读、文字与背景有足够对比、布局易读、控件靠近其影响的内容。

因此，“更 Apple”应进入 `design.md` 的体验原则与验收条目，而不是写成“使用毛玻璃、大圆角、SF 字体”。来源：[Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/)、[Apple UI Design Dos and Don’ts](https://developer.apple.com/design/tips/)。

### Chromium：设计文档应跟代码一起版本化和可发现

Chromium 把设计文档放在源码仓库中，以 Markdown 维护并自动渲染；文档按具体架构主题拆分，而不是依赖一份无限增长的总文档。

这支持 Living Reader 采用“根设计基线 + 专题设计文档”的方式。来源：[Chromium Design Docs](https://chromium.googlesource.com/chromium/src/+/main/docs/design/README.md)。

## `design.md` 应负责什么

- 产品问题、目标用户与关键证据。
- 版本目标、非目标和不可突破的体验边界。
- 核心用户链和状态转换。
- 信息架构、交互原则和视觉原则。
- 已接受的关键设计决策及理由。
- 跨模块共同遵循的可验收体验规则。
- 未决问题、负责人、裁决方式和变更记录。
- 指向详细流程、视觉规范、架构协议、原型、审计和任务记录的索引。

## `design.md` 不应负责什么

- 不复制 Teable 的任务状态、负责人和实施排期。
- 不复制架构文档中的 schema、事件协议和内部实现细节。
- 不收纳每轮浏览器问题清单；这些进入审计报告和 Teable。
- 不把某张参考图直接宣布为最终设计，而不记录采用了它的哪些特征。
- 不把当前实现倒写成长期原则。
- 不成为颜色、字号和组件状态的完整 token 手册；详细规范应拆分并由根文档索引。

## 推荐结构

### 0. 文档元信息

回答：当前状态是什么？谁负责？谁拥有最终视觉判断？最后一次审查是什么时候？哪些章节仍未确定？

建议字段：`Status`、`Owner`、`Visual approver`、`Last reviewed`、`Applies to`、`Supersedes`。

### 1. 一句话产品设计

回答：用户最终获得什么独特价值？这句话能否帮助团队拒绝不相关功能？

### 2. 问题、用户与证据

回答：谁在什么情境中遇到什么困难？这是观察、推断还是选择？引用哪些用户反馈、现有界面或研究？

### 3. 本版目标与非目标

回答：这一版必须证明什么？什么即使有价值也不在当前范围？成功的可见信号是什么？

### 4. 设计原则与反例

每条原则使用同一格式：

- 原则：我们优先保护什么。
- 理由：用户证据或产品机制。
- 可观察规则：界面必须怎样表现。
- 反例：什么看似符合但实际违背原则。

例如：

> 原则：书是主角，Agent 是可召回的边缘层。
>
> 可观察规则：首屏正文拥有第一视觉重心；任一状态只有一个主动作；hash 和 provider 默认不展示。
> 反例：只把轨道变窄，但仍常驻所有工程状态。

### 5. 端到端体验与状态

回答：用户行动触发什么状态？系统显示什么结果？如何停止、撤回、拒绝、失败和重试？

Living Reader 应覆盖：阅读 → 表达 → 核对 → 关系 → 规则预览 → 世界 → 行动反馈 → 返回证据。

### 6. 信息架构与界面职责

回答：什么属于内容层，什么属于操作层？哪些信息常驻、上下文出现、按需展开？桌面和移动端如何保持同一心智模型？

### 7. 关键交互合同

按体验表面记录，而不是按组件名记录：阅读定位、表达入口、Agent 回应、关系审阅、世界展开、证据回归、权限与停止。

每项至少写：进入条件、主动作、可见反馈、退出/撤回、失败分支、无障碍等价路径。

### 8. 视觉语言

回答：视觉层级、排版、色彩、空间、动效和内容素材服务什么体验目的？哪些参考只借结构、不借品牌外观？

详细 token 和组件状态放在专题文档；根文档只保存长期原则与硬约束。

### 9. 方案比较与决策记录

对重要分歧保留最小表格：

| 状态 | 问题 | 采用方案 | 拒绝方案 | 理由 | 证据/原型 |
|---|---|---|---|---|---|
| Proposed / Accepted / Rejected | 要裁决什么 | 当前选择 | 比较过什么 | 权衡 | 链接 |

### 10. 验收与反证

回答：什么证据会证明设计成立？什么现象会推翻当前判断？

至少包括：真实浏览器主链、桌面和移动视口、键盘与文字等价路径、失败/撤回、reduced motion、视觉对比，以及用户对关键品味轴的明确判断。

### 11. 未决问题

不要只列问题。每项应有：影响、负责人、需要的证据、裁决门槛和阻塞的后续任务。

### 12. 变更记录与权威关系

记录“改了什么、为什么改、替代了哪条决定”，并链接 Teable、ADR、原型和验收证据。实现状态变化不自动改写设计原则。

## 对当前 `design.md` 的评估

### 已经做得好的部分

- 有清晰的一句话设计，并且能排除“把书变成聊天故事”的方向。
- 首版证明目标和用户主路径明确。
- 来源、读者、Agent、关系、模型和世界的身份边界清楚。
- 语音、权限、停止和确定性世界的限制较完整。
- 已有完成定义和文档权威关系。

### 当前主要缺口

| 缺口 | 影响 |
|---|---|
| 缺少 Owner、审批者、状态语义和更新时间机制 | Draft、接受、实现和验证容易混淆。 |
| 缺少用户问题与证据章节 | 设计原则像内部主张，无法追溯到观察和用户判断。 |
| 没有独立的 Goals / Non-goals | 产品边界存在，但不利于逐版裁剪和评审。 |
| 没有备选方案与拒绝理由 | 后续 Agent 容易重新提出已被否决的 dashboard、SVG 或聊天优先方向。 |
| “尚待明确”没有负责人和裁决条件 | 问题会长期悬空，无法阻断错误实现。 |
| UI/UX 代码落点和当前工程状态写入根基线 | 这些信息变化快，容易让稳定原则过期。 |
| 缺少决策历史 | 新版本会覆盖旧理由，无法知道品味如何演化。 |
| 验收定义偏全产品，缺少逐个交互表面的反证条件 | 页面能打开仍可能被误当作设计完成。 |

## 建议的文档体系

```text
design.md                         # 产品设计宪法、已接受决策、索引
docs/design/
  experience-flow.md             # 用户动作、状态、反馈、失败和恢复
  visual-language.md             # 排版、色彩、空间、动效、素材原则
  responsive-accessibility.md    # 移动、键盘、缩放、reduced motion
  decisions/                     # 一项重要分歧一份短决策记录
docs/design-audit/               # 某次真实界面审计及截图证据
Teable                           # 任务、状态、负责人、依赖和验收证据
docs/architecture/               # schema、事件、权限和运行时协议
```

根 `design.md` 应保持短、稳定、能从头读完。只有跨模块、长期有效且已经形成决定的内容进入根文档；细节通过链接下沉。

## 写作检查表

提交任何 `design.md` 修订前检查：

- [ ] 开头能用三分钟解释产品问题、版本目标和核心方案。
- [ ] Fact、Inference、Decision、Open Question 没有混写。
- [ ] 每个目标都有可见成功信号，每个非目标都能阻止范围膨胀。
- [ ] 每条设计原则都有理由、可观察规则和反例。
- [ ] 关键用户链包含停止、撤回、拒绝、失败、重试和未知状态。
- [ ] 来源内容、读者内容、Agent 推断和模型扩展不会互相冒充。
- [ ] 重大方案记录了备选、权衡和拒绝理由。
- [ ] “更 Apple”等品味要求已经转成可判断的界面条件。
- [ ] 验收覆盖真实用户路径，不以 build 或页面打开替代体验证明。
- [ ] 未决问题有负责人、证据需求和裁决门槛。
- [ ] 易变的任务状态和代码清单留在 Teable/审计文档，而非根基线。
- [ ] 变更保留理由和历史，而不是只覆盖旧文本。

## 对 Living Reader 的下一步建议

先不要在当前文档末尾继续追加内容。下一轮应进行一次结构性改写：

1. 保留现有一句话设计、主路径、身份边界和权限边界。
2. 补入用户问题与证据、Goals / Non-goals、设计原则的反例。
3. 把当前 UI 问题和代码落点移到设计审计与 Teable，只在根文档保留长期结论。
4. 建立第一份决策比较：`始终可见的安静轨道` vs `可折叠书签态`。
5. 给每个未决问题加负责人、证据和裁决门槛。
6. 用户确认结构后，再从 Draft 0.2 升为 Draft 0.3；不在本轮调研中直接改写。
